# Вариант 19 · АРМ администратора кафедры

[Қазақша](README.md) · [Русский](README.ru.md) · [English](README.en.md)

Учебная система управления доступом и журналирования: FastAPI, SQLite, HTML/CSS и обычный JavaScript. Регистрация, серверные сессии, RBAC, задания, оценки, документы и аудит работают без AI. Локальные Ollama и многоязычная embedding-модель используются только дополнительным помощником по аудиту.

Интерфейс полностью переключается между казахским, русским и английским. Выбор языка на странице входа и в верхней панели сохраняется в localStorage; даты и числа форматируются через `Intl`. Имена, текст работ и исходные причины событий остаются данными на языке автора.

Seed содержит 3 группы, 12 вымышленных студентов, 3 предмета, 2 семестра, 72 оценки и 40 примеров аудита. Имена придуманы для этой учебной системы и не обозначают реальных людей; случайные совпадения возможны. Подключения к университетским системам нет. Аккаунты с известными паролями не создаются.

## Установка и запуск

Нужен Python 3.11+. Выполняйте все команды из корня репозитория. Если рабочая `.venv` уже существует, не создавайте её повторно. Новая установка в Windows PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e '.[dev]'
Copy-Item .env.example .env
.\.venv\Scripts\python.exe -m app.seed
.\.venv\Scripts\python.exe -m app.bootstrap --login YOUR_LOGIN --name "YOUR_DISPLAY_NAME"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Замените `YOUR_LOGIN` и `YOUR_DISPLAY_NAME` своими значениями. Bootstrap дважды запрашивает пароль скрытым вводом в интерактивном терминале: 12–128 символов. Не передавайте пароль аргументом, через `.env` или документацию. Если первый администратор уже существует, команда не создаёт второго и не меняет пароль. Других администраторов назначает действующий администратор.

Откройте **http://127.0.0.1:8000** и войдите созданным аккаунтом. Остановка сервера: `Ctrl+C`. При другой поддерживаемой версии Python замените `-3.12` соответствующим номером.

Linux/macOS: `python3 -m venv .venv`, затем `. .venv/bin/activate`; используйте `python` вместо Windows-пути и `cp .env.example .env` вместо `Copy-Item`. Остальные команды те же.

Сервер также подготавливает схему и учебные данные при старте. Повторный `python -m app.seed` не добавляет дубликатов и не сбрасывает оценки, имена, аккаунты или пароли. Сохранена прежняя команда `python -m app.db` для примеров аудита.

## Регистрация, одобрение и роли

1. Зарегистрируйтесь с запросом роли «Преподаватель» или «Студент». Запрошенная `requested_role` хранится отдельно от фактической `role_code`. Запросить администратора, заведующего или аудитора через регистрацию нельзя.
2. С правильным паролем можно войти сразу, но до одобрения доступен только личный статус заявки и выход. Закрытые API возвращают `403`; ожидающая или отклонённая заявка не выдаётся за неверный пароль.
3. Администратор проверяет «Заявки на регистрацию» и одобряет либо отклоняет с объяснением. Заявка преподавателя получает только роль преподавателя; позднее роль меняется отдельно в разделе пользователей. Решение и изменение роли записываются в аудит.
4. Для студента выберите существующую запись либо добавьте её по проверенным сведениям, подтвердив группу. Одна запись связывается только с одним аккаунтом. Сам студент менять связь не может; изменение администратором аудитируется. Преподавателю затем назначают точные группу, предмет и период через «Преподаватели → Профиль преподавателя → Добавить учебное назначение».

Права читаются из базы при каждом защищённом запросе. Скрытие кнопки не заменяет серверную проверку. Прежняя авторизация через `X-Demo-User` удалена.

При регистрации студента отдельно запрашиваются полное имя, студенческий ID/номер зачётной книжки и учебная группа. Номер очищается от пробелов по краям и переводится в верхний регистр; допустимы 3–32 ASCII-буквы/цифры/`_`/`-`. Это **неподтверждённые сведения заявки**, а не имя аккаунта или готовая связь с `Students`. В форме преподавателя эти поля скрыты, отключены и отсутствуют в payload. Публичный `GET /api/auth/registration-options` возвращает только группы и требования к email, без списка студентов.

В списке заявок номер маскируется. Полный номер и email доступны только на личной странице владельца и в окне администратора `GET /api/admin/requests/{id}`. Администратор проверяет заявленные имя, код и группу, затем сам выбирает существующую запись либо подтверждает добавление в проверенную группу; предварительного выбора студента, группы и отмеченных подтверждений нет. Для одобрения требуется `confirm_student_match=true`. При связывании с существующей записью расхождение либо отсутствие сведений в старой заявке требует отдельного `acknowledge_mismatch=true`; при сомнении заявку можно вернуть на проверку. При каждом одобрении студента сервер также требует непустой актуальный `claim_revision` из ответа с приватными сведениями: отсутствие даёт 422, изменение сведений — 409; в последнем случае заявку нужно открыть и проверить заново.

`POST /api/admin/requests/{id}/needs-review` сохраняет причину и оставляет аккаунт ожидающим, неактивным и без связи. Владелец видит только свою причину и может исправить данные через `PUT /api/auth/student-claim`, отправив заявку на повторную проверку. Одобренный студент не может менять таким способом сведения или связь. Роль, активация и выбранный `student_id` сохраняются атомарно; второй аккаунт для уже связанного студента получает `409`. Старые коды `SYN-001..012` остаются действительными. Пароли, полные номера из неподтверждённых заявок и email не попадают в общий аудит, серверные логи или общий список заявок. Уполномоченные сотрудники видят сохранённый официальный студенческий код в списке студентов.

В окне одобрения по умолчанию предлагается **выбрать существующего студента**, отдельно можно **добавить студента по проверенным сведениям**. При добавлении администратор сам выбирает реальную группу из каталога и явно подтверждает имя, код и группу; группа и флажок заранее не выбираются. UI отправляет `create_student=true`, `confirmed_group_id`, `confirm_student_match=true` и свежий `claim_revision`, без `student_id`. Сервер повторно использует точное совпадение. Конфликт кода всегда даёт `409 student_selection_required` и требует ручного выбора. Если совпадает только полное имя, а код отличается, администратор сравнивает существующие записи и отдельно подтверждает другого человека перед добавлением с `confirm_distinct_student=true`. Этот флажок сбрасывается при смене группы или способа и не обходит конфликт кода. Запись `Students` и связь с аккаунтом сохраняются в одной транзакции. До одобрения заявка не создаёт официальную запись в списке студентов.

Раздел **Студенты** показывает реальные записи `Students`: имя, код и группу из каталога. «Все группы», фильтр группы и поиск по имени/коду совместно выполняются на сервере через `GET /api/students?group_id=…&q=…&page=1&page_size=25`; пустой `group_id` не передаётся. Нужна фактическая роль admin, head или teacher и право `Grades.View` либо `Users.Manage`. Преподаватель видит только назначенные группы; студенту и аудитору список недоступен. Пустой каталог, отсутствие результатов и ошибка сервера показаны отдельно. Регистрация и исправление нормализуют пробелы в имени и проверяют длину 2–120 символов; пустой каталог групп блокирует отправку студенческой заявки. Преподавателю поля студента не требуются.

| Роль | Доступ по умолчанию |
|---|---|
| Администратор | Управление аккаунтами, ролями, сессиями, аудитом и учебными разделами |
| Преподаватель | Студенты назначенных групп, назначенные ведомости, документы, задания и проверка работ |
| Студент | Опубликованные задания своей группы, собственные работы и опубликованные результаты |
| Заведующий кафедрой | Список студентов, просмотр учебных данных и аудита без изменения оценок |
| Аудитор | Панель управления и аудит, без изменения учебных данных |
| Ожидающий / отклонённый | Только вход, личный статус заявки и выход |

Коды `Learning.View`, `Learning.Manage`, `Learning.Submit` дополняют права Dashboard/Users/Roles/Grades/Documents/Sessions/Audit. Scope предмета, группы и семестра проверяется отдельно. Студент не получает административный доступ или аудит даже при ошибочном назначении этих кодов. Последнего активного администратора нельзя отключить, понизить или лишить основных прав управления.

## Одобрение преподавателя и учебная нагрузка

1. Регистрация преподавателя остаётся pending/inactive и не требует студенческих полей. В **Преподаватели → Заявки преподавателей** администратор ищет заявку, открывает профиль и одобряет либо отклоняет с короткой причиной. В любой точке одобрения заявка преподавателя получает только `teacher`; выбора роли нет. Позднее роль меняется отдельным действием в общем разделе пользователей. Общий раздел пользователей сохранён для системного управления аккаунтами и ролями.
2. Недостающие группы, предметы и периоды добавляются в **Группы и предметы**. Для периода нужен учебный год. Записи можно переименовать, архивировать и восстановить; DELETE API нет. Архивация сохраняет старые связи оценок/заданий/аудита, но запрещает новые назначения и задания с этой записью.
3. Откройте **Преподаватели → Список преподавателей → Профиль преподавателя → Добавить учебное назначение** и выберите точные группу, предмет и период вместе. Можно добавить несколько строк; одинаковый tuple не дублируется. Изменение выполняет атомарный `PATCH /api/academic/assignments/{assignment_id}`, отзыв использует прежний `PUT /api/academic/assignments`. Профиль и основной список после изменений перечитываются.
4. **Моя учебная нагрузка** на главной странице преподавателя показывает действующие точные комбинации. Форма задания выбирает одно полное назначение, а не независимые списки. Без назначений создание задания скрыто, учебные разделы объясняют необходимость обратиться к администратору кафедры. Архивация каталога или отзыв назначения сразу меняет доступ и в текущей сессии.
5. Отключение преподавателя завершает активные сессии; восстановление аккаунта не оживляет старые токены. Отказ по заявке преподавателя через любую точку входа также завершает pending-сессии; после нового входа доступен только личный статус отклонённой заявки.

Серверные фильтры/пагинация работают через `GET /api/admin/teachers`: вид, статус, поиск, группа, предмет. Профиль — `GET /api/admin/teachers/{id}` и отдельные approve/reject/active endpoint-ы. Каталог — `GET/POST/PATCH /api/admin/catalogs…`. Для обеих административных страниц нужны фактическая роль admin и `Users.Manage`. Своя действующая нагрузка — `GET /api/academic/workload`. Изменение и аудит сохраняются одной транзакцией; права и точный tuple проверяются по базе при каждом запросе.

## Задания, работы и оценки

«Документы → Загрузить» сохраняет общий учебный документ, не создавая задания или дедлайна. Для работы студента используйте «Задания → Создать задание». Выбранный в этой форме начальный материал отправляется через `POST /api/tasks/with-material`: файл, задание и аудит сохраняются вместе. Ошибка файла, изменение scope или сбой аудита не оставляют опубликованное задание либо новый файл. JSON `POST /api/tasks` сохранён для заданий без материала; материал можно добавить позже.

Новый или изменённый дедлайн должен быть в будущем по часам сервера (`422 deadline_in_past`). Уже закрытое задание можно редактировать без изменения его прежнего дедлайна, включая название, правила и разрешение поздней сдачи. Нетронутые поля даты сохраняют исходные UTC-секунды и микросекунды. Переданные клиентом `now`, `student_id` и даты не заменяют серверную проверку времени и владельца.

Преподаватель создаёт задание, выбрав одно полное назначение группы/предмета/периода, и вводит название, описание, время публикации и обязательный дедлайн. Можно добавить правила сдачи и безопасный файл материала. Студент видит только опубликованные задания своей группы и собственные работы; замена ID в API не открывает чужую работу.

До дедлайна работу можно отправлять и обновлять. При `now >= deadline` первая и повторная сдача по умолчанию закрыты. Явное `allow_late=true` разрешает и позднюю сдачу, и обновление; работа отмечается как поздняя. Дедлайн хранится в UTC, а форма и интерфейс показывают местный часовой пояс.

Преподаватель своего предмета/группы ставит целую оценку `0..100`, пишет комментарий и отдельно выбирает публикацию. Неопубликованные оценка, комментарий и сведения о проверяющем студенту не выдаются. Пересдача очищает предыдущую проверку и публикацию; новую версию нужно оценить снова. Проверка версии предотвращает потерю параллельных изменений. После появления работ нельзя менять предмет/группу/семестр задания.

Изменения оценки и её истории сохраняют автора, UTC, IP и старое/новое значение вместе с аудитом в одной транзакции. Полные тексты работ и комментариев в аудит не копируются. AI не оценивает работы. Кнопка «Справка» повторно открывает 2–5 конкретных шагов для текущей роли и страницы.

Точные прежние/новые отзывы, оценки, публикация и версии сохраняются в `SubmissionReviewHistory` вместе с actor, UTC, IP и audit ID в одной транзакции. Окно истории проверки и `GET /api/submissions/{id}/history` доступны только уполномоченным сотрудникам в пределах scope; студент не получает из истории неопубликованные результаты. Общий аудит хранит хэши отзывов и необходимые метаданные оценок и версий, без текста частного отзыва.

## Документы, сессии и аудит

Документы и вложения: PDF, UTF-8 TXT, PNG, JPEG, по умолчанию до **5 МиБ**. Проверяются расширение, MIME, содержимое и размер. Сервер создаёт UUID-имя; путь не строится из пользовательского имени. Выдача — после проверки прав, как attachment. Загрузка, просмотр, удаление и действия с учебными файлами аудитируются. Удаление документа мягкое: запись исчезает из списка, физический файл сохраняется.

Журнал показывает автора, роль на момент события, UTC, IP, действие, объект, результат и необходимые старые/новые значения. Есть фильтры по дате, пользователю, действию, результату и IP, страницы и полная запись по audit ID. API редактирования/удаления аудита отсутствуют; SQLite-триггеры также запрещают UPDATE/DELETE.

Подозрительные сессии отмечают объяснимые правила: несколько неудачных входов по логину/IP или смена IP за короткий интервал. Создаются причина, audit ID и статус `awaiting_admin`, без автоматической блокировки. Администратор изучает доказательства и с причиной блокирует сессию либо отмечает ложное срабатывание. Новый триггер после отклонённого признака снова требует проверки. Rate limit работает независимо.

AI может объяснить только уже записанные доказательства с явной отметкой рекомендации. Он не объявляет угрозу фактом и не принимает решение о блокировке. Блокировка немедленно делает токен недействительным. Снятие блокировки переводит сессию в `revoked`, не оживляя прежний токен: пользователь входит снова. Отключение аккаунта завершает его активные сессии.

Выбранные AI ссылки не заменяют доказательства правила: связанные неудачные входы передаются в безопасной проекции, исходные и параллельно добавленные ID сохраняются для администратора. Причина решения после удаления управляющих символов должна содержать не менее пяти значимых символов.

## Безопасность и настройки

Пароли хранятся как scrypt с уникальной солью (`N=32768, r=8, p=3`). Случайный session token передаётся в `HttpOnly`, `SameSite=Strict` cookie; в базе только SHA-256 хэши токена и привязанного CSRF. Изменяющие запросы проверяют `X-CSRF-Token`, Origin и Fetch Metadata. При HTTPS задайте `COOKIE_SECURE=true`. Ошибки входа не раскрывают наличие аккаунта; лимит попыток хранится в SQLite.

SQL использует параметры, интерфейс выводит недоверенный текст через `textContent`, действует CSP. Пароли, cookie, токены и embedding-векторы не записываются в аудит. По умолчанию IP берётся из socket peer. `X-Forwarded-For` учитывается только для явно доверенного непосредственного proxy; цепочка проверяется справа налево.

| Переменная `.env` | Значение по умолчанию |
|---|---|
| `DATABASE_PATH` / `UPLOAD_DIR` | `data/audit.db` / `data/uploads` |
| `MAX_UPLOAD_BYTES` / `SESSION_TTL_SECONDS` | `5242880` / `28800` |
| `COOKIE_SECURE` | `false` для локального HTTP; `true` для HTTPS |
| `STUDENT_EMAIL_REQUIRED` | `false`; `true` делает email учебного заведения обязательным для студентов |
| `STUDENT_EMAIL_DOMAIN` | пусто; при заполнении сервер проверяет домен email, например `example.edu` |
| `LOGIN_MAX_ATTEMPTS` / `LOGIN_WINDOW_SECONDS` | `5` / `300` |
| `SUSPICIOUS_FAILURE_THRESHOLD` / `SUSPICIOUS_WINDOW_SECONDS` | `3` / `600` |
| `ALLOWED_ORIGINS` | `http://127.0.0.1:8000,http://localhost:8000` |
| `TRUSTED_PROXIES` | Пусто; при необходимости IP/CIDR через запятую |
| `OLLAMA_BASE_URL` / `OLLAMA_MODEL` | `http://localhost:11434` / `qwen2.5:1.5b` |
| `EMBEDDING_MODEL` / `EMBEDDING_PREFIX` | `models/multilingual-e5-small` / `query: ` |
| `SEMANTIC_THRESHOLD` / `LLM_TIMEOUT_SECONDS` / `MAX_CANDIDATES` | `0.80` / `180` / `500` |

Относительные пути считаются от текущего рабочего каталога процесса: запускайте сервер из корня репозитория. После изменения настроек перезапустите сервер. При другом адресе/порте обновите `ALLOWED_ORIGINS`. Не сохраняйте секреты в `.env.example` или Git. Для резервной копии сохраняйте SQLite и uploads вместе.

## Необязательные локальные AI-модели

Сначала [отдельно установите приложение/CLI Ollama](https://ollama.com/download/windows): Python extra `.[models]` его не устанавливает. Затем:

```powershell
.\.venv\Scripts\python.exe -m pip install -e '.[models]'
ollama serve
```

Во втором терминале:

```powershell
ollama pull qwen2.5:1.5b
.\.venv\Scripts\python.exe scripts/download_embedding.py --model intfloat/multilingual-e5-small --output models/multilingual-e5-small
```

Уже имеющиеся модели не загружайте повторно. Первичная подготовка скачивает файлы; inference выполняется локально, без API-ключей и внешних LLM/embedding API. Embedding работает с `local_files_only=True`, `trust_remote_code=False`. Ollama разрешён только на loopback, без redirect и proxy environment. Параметры генерации сохранены: `num_predict=512`, `num_ctx=4096`.

Закрытая схема AI принимает только проверенные даты, действия, результат, логин, IP, объект, semantic query и лимит. Неизвестные поля и неверный JSON отклоняются; SQL всегда составляет backend с параметрами. Примеры: `login: teacher.one`, `IP: 203.0.113.17`, `object: grade/17`, `action: submission_review`. Embedding сравнивает только безопасный reason уже отфильтрованных SQL-записей. IP и old/new не передаются модели. Каждое утверждение связано с реальными audit ID; текст журнала, включая prompt injection, остаётся данными.

Нажатие готового вопроса сразу запускает реальный поиск; примеры и отправка недоступны до его завершения. Некорректные явные login/IP/action/object возвращают `422 invalid_search_filter`, а не игнорируются. Точка в конце предложения считается пунктуацией; идентификатор с намеренной конечной точкой заключите в кавычки: `login: "teacher.one."`.

E5 использует `query: ` для обоих сравниваемых текстов. Порог `0.80` — настраиваемая мера сходства, не вероятность риска. «Последняя неделя» — 7×24 часа назад от UTC now, «сегодня» — с полуночи UTC. Интервал `[start_at,end_at)` не включает конец. Недоступная модель даёт понятную ошибку AI, не отключая остальные разделы.
